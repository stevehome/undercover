# Tech stack

- `backend/`: FastAPI. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount, and a sign-off only records who signed off and when: the agent pays. The payout rules (`payouts.py`, from the policy wording and the plans) are an operation too, and the one place that knows the sign-off limit in `data/company.json`. The policy wording and the claims manual are stored split into their headed sections, read by section rather than handed over whole. All our records live in the database: the claims (content and state), policies, customers, plans, add-ons, handlers, company settings and those documents, with steps, cost and time (`model_calls`, `work_segments`), the runs (`runs`, with a partial unique index so only one is `running`, and `run_claims`, one row per claim a run works with its status and attempts), the held-out claims and the handlers' decisions on the two labelled sets (`held_out_claims`, `answer_key`, which no claim operation reads, and which only `seed_data.py`, `evaluations.py` and `scoring.py` touch). The files in `data/` are only the starting data: `seed_data.py` reads them, the one place that does, when a database is empty, and after that the rows are the source. The records are in a database through SQLAlchemy Core, so each query is written once: Supabase Postgres when `DATABASE_URL` is in the environment (`npm run dev` passes `.env`; the tests never do), SQLite otherwise. On Postgres all our tables, the agent's saved progress included, are in the `undercover` schema, and a process uses at most 4 connections (the free plan allows 15 through the session pooler, across every process). `npm run seed` resets the database. Routes in `main.py` are thin; claim and run logic is in `claims.py` and `runs.py`, and `NotFound` and `Conflict` errors become 404 and 409 in one place. Money is `Decimal` dollars in Python, a two-decimal string on the wire and whole cents in the database (`backend/money.py`). A claim is decided once and paid once, enforced by a conditional `UPDATE`; repeating a decision or payment already recorded returns the claim, and a different decision on a decided claim is a 409. One agent works a claim at a time: it leases the claim for 30 seconds (`acquire_lease`, which the same agent calls again to renew, and `release_lease`), and a dispatch hands a claim with a live lease to the claim agent, which leaves it to its holder. A dispatch and an evaluation are both runs: an evaluation works copies of a labelled set's claims, with ids such as `EVAL-7-CLM-1203` and `evaluation_run_id` set, which the queue, a dispatch and sign-off never touch, and the backend scores it from its own records (`scoring.py`, pure `Decimal` functions with the lab's measures). The backend starts a run by asking the agent's service (`agent_service.py`, 409 while a run is going, 503 when the service is down). The database waits up to 10 minutes for a free connection, since up to 25 claim agents share 4. After a sign-off the backend tells the agent's service (`UNDERCOVER_AGENT`, or `http://127.0.0.1:8002`), once the sign-off is saved and without waiting for the payment.
- `agent/`: the claim agent is a hand-written LangGraph graph (`claim_graph.py`, `claim_nodes.py`, `claim_state.py`) whose progress is saved after every step in the same Supabase database by LangGraph's synchronous Postgres checkpointer (`checkpoint.py`, with `durability="sync"`; one pool of 4 connections that claims wait for, and a saver of its own for each claim worked, because a saver locks around every read and write). Its nodes call the model with the tools, read the decision back from the backend, wait for a sign-off with `interrupt()` when the backend says one is needed, and pay. `dispatcher.py`, the fifth part of the agent, is a LangGraph graph with no model, in the style of the Week 2 Day 4 lab: a node lists a run's claims, a conditional edge sends each to a `work_claim` worker with one `Send`, and `max_concurrency` is N. It works dispatches and evaluations alike. Each claim keeps its own thread and saved progress, never a shared thread or a subgraph, because a claim can wait days for a sign-off; the dispatcher saves none. The worker has `RetryPolicy(retry_on=(ModelRateLimitError, ModelTimeoutError))`, which `work.py` lets through without settling the claim, so a retry carries the claim on from its last saved step as the same attempt, and an `error_handler` that leaves the claim `still in progress` for the next dispatch when the waits run out. It needs langgraph 1.2.20 or later. Both reach claims, documents and instructions only through the backend's API; `api.py` is the only module that makes HTTP calls, to the backend at `UNDERCOVER_BACKEND` or `http://localhost:8000`. `harness.py` builds the model and says which it is (`model_settings()`; generic, no claims). `tools.py` holds every tool, each reading its state from `ToolRuntime[ClaimContext]` (in `contexts.py`, with the claim's run). `agents.py` wires the claim agent: `decide_claim(claim_id, ..., run_id)` starts a claim or carries it on from its saved thread, and it is the only function the dispatcher's worker reaches the claim agent through, so that later it can point at the agent in the cloud. `work.py` is the retry policy, deterministic Python rather than left to the model: a failed claim goes back in the queue on a new thread and is tried once more, then left for a handler; a stopped claim carries on without a new attempt. A referred claim is left for a handler, and a claim's note is one line built from the recorded decision. `__main__.py` works one claim (`uv run -m agent CLM-1001`), and `service.py` is the agent's web service, a fourth entry point, which `npm run dev` starts beside the backend and the dashboard on port 8002: it carries a claim on after a sign-off, starts dispatches and evaluations (answered at once, 409 while a run is going, worked in the background), and when it starts it marks any run still running as stopped. `lease.py` holds a claim's lease while `decide_claim` works it, renewing it from a background thread every 10 seconds, so a crashed agent's claim is free to carry on after 30 seconds; a claim another agent holds is left to that agent. `tracing.py` sends each claim's work to Langfuse, in one session named after the claim and its thread, tagged `run-<id>` (`langfuse_tags`) so a whole run is found together. The model has a request timeout and a claim fails after 30 model calls. The default model is `openai/gpt-6-luna` at low reasoning effort, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, which runs with no reasoning effort set. The model node records each reply's tokens and cost, and `timing.py` records each stretch of work on a claim (not a wait for a sign-off), through the backend into `model_calls` and `work_segments`. Model cost is the exception to whole cents: the database keeps whole billionths of a dollar, because OpenRouter reports costs to nine places, and the wire carries a decimal string. An evaluation's claims are never signed off, so once one is worked its saved progress is cleared, even when it is held for a sign-off.
- `dashboard/`: React, Vite and TypeScript. The queue page starts dispatches and shows the latest run; the Scoreboard page starts evaluations and lists them with their measures.
- `e2e/`: Playwright tests. They run the backend on SQLite and point it at a stand-in for the agent's service on port 8003.
- `data/`: the business data the database is first filled from. The agent never sees `data/evals/`, which holds the answer key; only seeding reads it, into tables no claim operation reads.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. The OpenRouter key is `OPENROUTER_API_KEY` in `.env`, with `DATABASE_URL` (the Supabase session pooler) and the Langfuse keys.
