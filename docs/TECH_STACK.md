# Tech stack

- `backend/`: FastAPI. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount, and a sign-off pays: one conditional `UPDATE` records the signed-in handler, the time and the payment (the payout, to the cent, at the same time) and sets the claim `decided`, only on a claim waiting for sign-off. A claim whose payment the Gateway refused is held by `POST /api/claims/{claim_id}/hold` (`hold_for_sign_off`, the agent's key only and not in the agent's API document): an approved, unpaid claim goes to waiting for sign-off with a `hold_reason` of `gateway`, and a sign-off then pays it. A claim's steps (`claim_steps`) each have a kind (`StepKind`: `note`, `tool_call`, `lookup`, `memory_search`, `memory_save` or `refusal`) and details of their own: a lookup's files with their sources, a memory search's finds, a memory save's events, a refusal's source and reason; a step of an unknown kind is a 422. The agent's payment operation refuses any amount over the approval limit with a 403 that names the limit, before it looks at the claim. The payout rules (`payouts.py`, from the policy wording and the plans) are an operation too, and the one place that knows the sign-off limit in `data/company.json`. The policy wording and the claims manual are stored whole, each with its version, in `documents`, and the plans in their own tables, all loaded at seeding from `context/` (`seed_data.py`, the one backend module that reads it, and only while seeding, since the app's Lambda package has none); the claim agent reads the documents through the context layer, not the app. All our records live in the database: the claims (content and state), policies, customers, plans, add-ons, handlers, company settings and those documents, with steps, cost and time (`model_calls`, `work_segments`), the runs (`runs`, with a partial unique index so only one is `running`, and `run_claims`, one row per claim a run works with its status and attempts), the held-out claims and the handlers' decisions on the two labelled sets (`held_out_claims`, `answer_key`, which no claim operation reads, and which only `seed_data.py`, `evaluations.py`, `scoring.py`, `grading.py` and `improver_view.py` touch). The files in `data/` are only the starting data: `seed_data.py` reads them, the one place that does, when a database is empty, and after that the rows are the source. The records are in a database through SQLAlchemy Core, so each query is written once: Supabase Postgres when `DATABASE_URL` is in the environment (`npm run dev` passes `.env`; the tests never do), SQLite otherwise. On Postgres all our tables, the agent's saved progress included, are in the `undercover` schema, and a process uses at most 4 connections (the free plan allows 15 through the session pooler, across every process). `npm run seed` resets the database. Routes in `main.py` are thin; claim and run logic is in `claims.py` and `runs.py`, and `NotFound` and `Conflict` errors become 404 and 409 in one place. The payout calculation is an operation on the claim (`POST /api/claims/{claim_id}/payout`, `calculate_payout`): it works the payout on the claim's own policy and keeps it for the claim's attempt (`calculations.py`, one for each claim and `thread`, so a claim worked afresh starts without one). A decision is checked against claims manual section 14 (`decision_record.py`): a blank reason, section or maker, an approval that pays nothing, and a decline or referral that pays something are refused by the request's own checks, before the claim is looked at and so with the same answer on any claim, each message naming section 14; an approval also needs the attempt's calculation on file and a payout equal to it (`Invalid`, 422). The claim then holds the calculation's lines (`calculation`), who made the decision (`decided_by`), when (`decided_on`) and the claims manual's version in force (`manual_version`, from `documents`), and a sign-off adds who and when. Money is `Decimal` dollars in Python, a two-decimal string on the wire and whole cents in the database (`backend/money.py`). A claim is decided once and paid once, enforced by a conditional `UPDATE`; repeating a decision or payment already recorded returns the claim, and a different decision on a decided claim is a 409. One agent works a claim at a time: it leases the claim for 30 seconds (`acquire_lease`, which the same agent calls again to renew, and `release_lease`), and a dispatch hands a claim with a live lease to the claim agent, which leaves it to its holder. A dispatch and an evaluation are both runs: an evaluation works copies of a labelled set's claims, with ids such as `EVAL-7-CLM-1203` and `evaluation_run_id` set, which the queue, a dispatch and sign-off never touch, and the backend scores it from its own records (`scoring.py`, pure `Decimal` functions with the lab's measures). The backend starts a run itself (`starts.py`: 409 naming the work going, one piece of work at a time) and asks the agent to work it (`agent_service.py`: 409 when the agent refuses, 503 when it didn't take it, 504 when it is unknown). The database waits up to 10 minutes for a free connection, since up to 25 claim agents share 4. The backend asks the agent (`UNDERCOVER_AGENT`, or `http://127.0.0.1:8080`) to work what it created, and to resume a claim after a sign-off or a send back; a sign-off pays whether or not the agent answers. The agent's operations are described in an OpenAPI document built from the app's own routes (`agent_api.py`, `GET /api/agent/openapi.json`): `get_claim`, `calculate_payout`, `decide_claim` and `pay_claim` (searching and reading the documents moved to the context layer), with no servers and no key, for the gateway that will serve them. A money input is `Decimal` in Python but `number` in the document, since the Gateway can't take the `anyOf` that `Decimal` gives (`Amount` in `money.py`); the app still accepts a number or a string. Likewise a decision is `string` in the document, since the Gateway makes an enum its own Cedar type that a policy can't compare with a string (`DecisionKind` in `main.py`); the app still allows only `approve`, `decline` and `refer`. Sign-in: `auth.py` checks a handler's Supabase access token with PyJWT's `PyJWKClient` against `<VITE_SUPABASE_URL>/auth/v1/.well-known/jwks.json` (audience `authenticated`), finds the handler by the token's email, and gives the routes `signed_in_handler` and `senior_handler` (who can sign off over the limit); `Unauthorized` and `Forbidden` become 401 and 403 in the one place that turns the other errors into responses; `GET /api/me`. A dispatch, an evaluation, a sign-off (which takes no handler id: it records the signed-in handler), a round, a proposal's decision and a setting's change need a handler; every other route needs the agent's API key or a handler, by its kind. `api_key.py` checks the `X-API-Key` header against `UNDERCOVER_API_KEY` with `secrets.compare_digest`, read as each request arrives; an unset key matches nothing. A route is for the agent (the key only), shared (`access.py`: the key or a signed-in handler: the claims, a claim, a run, the models, the recipes, a round) or for a handler (`signed_in_handler` or `senior_handler`), and only `GET /api/health` is open; a test asks every route for its answer with no credentials. The agent's one HTTP function (`agent/backend_http.py`, `send`) adds the key as each request is sent, and the agent's service won't start without it. Settings (`platform_settings.py`): the approval limit, the objectives, the noise, the tolerance, the spending limit and the agents at once are rows in `settings`, seeded from `data/company.json` and `data/improvement.json`, validated on change and recorded with who and when in `setting_changes`; the models allowed are the `models` table, seeded from `data/models.json`, read only, and with `MODEL_NAME` set the one model allowed is that one at effort `default` and price 0. Versions: `configurations` and `recipes` (`versions.py`; version 1 is seeded from `data/claim_instructions.md` and `data/improver_recipe.md`), each with its reason, who proposed and approved it, its round and a verdict, the current version being the highest kept one; `diffs.py` turns two texts into lines with `difflib`; every run records its `configuration_version`, and the claim agent gets its version through `get_current_configuration` and `get_run_configuration`, which hold no scores. The judge (`judge.py`, `grading.py`): Jev, `typesafe/jev-1.13`, through OpenRouter's Decisions endpoint with the lab's three questions, called once in `judge.py` with `server_url` (`OPENROUTER_ORIGIN`), a 10-second timeout and no retries; finishing an evaluation grades its claims in parallel and stores each grade, its two checks and its cost in `claim_grades`, apart from the claim agent's cost; a claim the agent didn't decide gets an F with no call, and with `MODEL_NAME` set the judge isn't called. Rounds (`rounds`, `proposals`, `improver_calls`; `rounds.py`, `proposals.py`, `round_view.py`, `improver_view.py`, `version_scores.py`, `verdict.py`, `spending.py`): a stretch of the improver's work is a run of kind `improver`, and a round's evaluations are runs with `parent_run_id` set, so the unique index on running runs applies only to runs with no parent; a version's scores average the whole-set evaluations its rounds ran on it; `verdict.py` is the keep-or-roll-back rule in `Decimal`; `spending.py` knows what a round has spent, what is left, what an evaluation will cost and whether a claim may start; the improver reads only `improver_view.py`, which holds the evaluation set's decisions and reasons and the held-out set's scores.
- `agent/`: the claim agent is a hand-written LangGraph graph (`claim_graph.py`, `claim_nodes.py`, `claim_state.py`) whose progress is saved after every step in the same Supabase database by LangGraph's synchronous Postgres checkpointer (`checkpoint.py`, with `durability="sync"`; one pool of 4 connections that claims wait for, and a saver of its own for each claim worked, because a saver locks around every read and write). The graph starts with the check for instructions hidden in a claim (`screening.py`: the security team's `SCREEN_INSTRUCTIONS` and a `Screening` model with `reason` and `instructions_found`, asked of GPT-6 Luna at reasoning effort `none` through Structured Outputs with `include_raw=True`, or of `MODEL_NAME`; `harness.screening_model()`). The `screen` node asks it up to three times when an answer can't be read, records each call and its cost with the claim and its run, records the first step, and saves its finding in the claim's state, so a claim carried on or signed off isn't checked again and a claim on a new thread is. A claim with an instruction goes to the `refer_flagged` node, which refers it with a payout of zero, the reason and the policy reference "Security check", and the claim agent's model never sees it. A rate limit or a timeout from the check goes up the same way as the claim agent's. Its nodes call the model with the tools, read the decision back from the backend, wait for a sign-off with `interrupt()` when the backend says one is needed (the sign-off itself pays, so a claim resumed afterwards only records it and ends), and pay a payout at or under the limit. `dispatcher.py`, the fifth part of the agent, is a LangGraph graph with no model, in the style of the Week 2 Day 4 lab: a node lists a run's claims, a conditional edge sends each to a `work_claim` worker with one `Send`, and `max_concurrency` is N. It works dispatches and evaluations alike. Each claim keeps its own thread and saved progress, never a shared thread or a subgraph, because a claim can wait days for a sign-off; the dispatcher saves none. The worker has `RetryPolicy(retry_on=(ModelRateLimitError, ModelTimeoutError))`, which `work.py` lets through without settling the claim, so a retry carries the claim on from its last saved step as the same attempt, and an `error_handler` that leaves the claim `still in progress` for the next dispatch when the waits run out. It needs langgraph 1.2.20 or later. Both reach claims, documents and instructions only through the backend's API; `api.py` (the claim agent's), `improver_api.py` (the improver's) and `backend_http.py` (the one client, to the backend at `UNDERCOVER_API` or `http://localhost:8000`, made on first use, and what a refusal looks like) are the only modules that make HTTP calls, and the claim agent's client has no way to the scores. The model's tools and the payment take one of two routes, chosen when a claim's context is built (`routes.py`, with the contract in `tool_route.py`): the Gateway's when `UNDERCOVER_GATEWAY_URL` is set (`gateway.py`: MCP tools named `<target>___<operation>`, `undercover-app` for the app, over streamable HTTP with every request signed with SigV4 for `bedrock-agentcore` by `sigv4.py`, using the AWS CLI's credentials and region; an amount goes as a JSON number, since the Gateway's schema says so, which is the one place the agent calls `float`), or direct (`direct.py`: the app with the key, as the rest of the agent calls it, and the context layer over MCP without signing, at `UNDERCOVER_CONTEXT` or `http://127.0.0.1:8006/mcp`). The context layer's seven tools are the model's tools on both routes, thin layers in `tools.py` over the route's `undercover-context` target. `mcp_connection.py` is the one place that calls an MCP endpoint from the synchronous agent, on an event loop of its own for each call that it closes without touching the thread's, so the main thread keeps the loop Mangum's tests need; `endpoints.py` reads `UNDERCOVER_API`, `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_CONTEXT` and `UNDERCOVER_MEMORY_ID` when asked, never at import. The model's tools take no id: they fill in the claim and who makes the decision from `ClaimContext`, so the model acts only on its own claim (the agent's `calculate_payout` works the claim's payout, and `decided_by` is "UnderCover Agent, configuration version N" for the version the run works to, or the security check for its referrals), and `get_claim` gives the model the same text on both routes (`claim_text.py`), which the check also reads. A refusal has a source, the app, the context layer or the Gateway's Policy (`refusals.py`): `step_recording.py` wraps each tool call and records it, so the tools record nothing themselves: a `tool_call` step named as the route names the tool before it runs, then a `lookup` step for a context-layer tool (what was looked up and the answer's files with their sources), a `memory_search` step, or a note; a refusal is recorded with its source and reason and handed to the model, so the claim's work goes on. A payment the Gateway refuses is recorded and the claim is held for a handler's sign-off (`hold_for_sign_off`), which pays it. The agent's bookkeeping (steps, model calls, work times, leases, the check's read and referral, the runs) goes straight to the app with the key, never through the Gateway. The memory (`memory.py`, `AgentCoreMemoryStore` from `langgraph-checkpoint-aws`, in the AWS CLI's region) is on when `UNDERCOVER_MEMORY_ID` is set and the claim isn't an evaluation's copy: the graph's `remember` node saves the decided claim as two events, the claim's summary, benefit, date, place and items as the customer's message and the decision with its payout, section and reason as the agent's, with the customer as the actor and the claim as the session, in code and once, since a node saves when it finishes; and `search_memory` is among the claim's tools only then (`claim_tools`), searching under `customers/<this claim's customer>` and leaving out the claim in hand. A claim the check referred never reaches `remember`. The checkpoints stay in Supabase. A failed save is logged and the claim keeps its decision, the one failure besides the dispatcher's that the agent lets go, and only AWS's own errors; a failed search reaches the model as a refusal. `harness.py` builds the models and says which they are (`model_settings()`, `improver_settings()` and `screening_model()`, which share the one read of `MODEL_NAME`; generic, no claims). `tools.py` holds every tool, each reading its state from `ToolRuntime[ClaimContext]` (in `contexts.py`, with the claim's run). `agents.py` wires the claim agent: `decide_claim(claim_id, ..., run_id)` starts a claim or carries it on from its saved thread, and it is the only function the dispatcher's worker reaches the claim agent through, so that later it can point at the agent in the cloud. `work.py` is the retry policy, deterministic Python rather than left to the model: a failed claim goes back in the queue on a new thread and is tried once more, then left for a handler; a stopped claim carries on without a new attempt. A referred claim is left for a handler, and a claim's note is one line built from the recorded decision. `__main__.py` works one claim (`uv run -m agent CLM-1001`), and `entrypoint.py` is the agent's AgentCore app (`BedrockAgentCoreApp`: `POST /invocations` and `GET /ping`, on port 8080, which `npm run dev` serves with uvicorn and reload) and it holds one entrypoint that calls `operations.handle`. A payload names an operation and its inputs (`work_run`, `work_round`, `carry_round_on`, `resume_claim`, `health`), each with a pydantic model, so a payload with an input missing or wrong, or an operation it doesn't know, is a 400 that says what; each answers `{"accepted": true}` (with the id of what it started, until the app creates it) or `{"refused": "<why>"}`, and the health check `{"healthy": true}`. `work_requests.py` checks that the work is what the app says it is (a run that is running, a round that is open, a proposal a handler has reviewed, which it reads from the app) and hands it to `jobs.py`, which tells the app every minute that the work is alive (`heartbeat.py`) and, when it fails, stops only its own run or round's stretch by id with the reason; `background_work.py` registers each piece of work with the AgentCore app as an async task before it answers and completes it when it ends, so the ping says `HealthyBusy` while anything is going. Nothing happens when the agent's code is imported: `readiness.py` gets ready on the first request, once in the process (on Runtime `credentials.py` reseeds the random numbers and fetches the three credentials from AgentCore Identity into their settings, `AGENTCORE_CREDENTIAL_<NAME>_NAME` naming each provider; then the agent's key is checked and the checkpoint pool opened; it marks nothing stopped, since the app does), and a failure answers its error and is tried again. `key_check.py` refuses a request without the agent's key as `Authorization: Bearer <key>` off Runtime, apart from the health check, and asks for none on Runtime, where AWS checks the caller. A claim waiting at `approval` is paused with `interrupt()`; `paused.py` reads the pause and what the app's record answers it with (a sign-off, or a send back with its note), and `resumption.py` refuses a resume of a claim that isn't paused or has no answer and otherwise works it, telling the app every minute (`heartbeat.py`) that it is. A send back (`review_message.py`) forgets the decision, gives the model the note as a review to check against the policy wording and the claims manual, and starts its model calls again. `lease.py` holds a claim's lease while `decide_claim` works it, renewing it from a background thread every 10 seconds, so a crashed agent's claim is free to carry on after 30 seconds; a claim another agent holds is left to that agent. `tracing.py` sends each claim's work to Langfuse, in one session named after the claim and its thread, tagged `run-<id>` (`langfuse_tags`) so a whole run is found together. The model has a request timeout and a claim fails after 30 model calls. A claim agent is built from the configuration version its run uses (the current one when it has no run): its instructions, model and reasoning effort, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, which runs with no reasoning effort set (recorded as `default`). The model node records each reply's tokens and cost, and `timing.py` records each stretch of work on a claim (not a wait for a sign-off), through the backend into `model_calls` and `work_segments`. Model cost is the exception to whole cents: the database keeps whole billionths of a dollar, because OpenRouter reports costs to nine places, and the wire carries a decimal string. An evaluation's claims are never signed off, so once one is worked its saved progress is cleared, even when it is held for a sign-off. The improver (`improver.py`, `improver_tools.py`, `rounds.py`): a LangChain `create_agent` on GPT-6 Luna at medium effort with `parallel_tool_calls` off and its model calls capped for each round, with `HumanInTheLoopMiddleware` on `propose_change` and `propose_recipe` (a middleware ahead of it sends a proposal outside the models allowed back to the improver, and others record its cost and end it when its round is stopped), the lab's four tools (`read_results`, `propose_change`, `run_evaluation`, `propose_recipe`) reading their state from `ToolRuntime[ImproverContext]`, and its own `PostgresSaver` with `durability="sync"`, a new thread for each round, so a round waiting for a handler survives a restart. `rounds.py` works a round in stretches: the first evaluations the current version lacks, then the improver until it pauses at a proposal, which is recorded with the backend; a handler's decision is recorded through the backend first (refused with 409 if something else is running), then the improver is resumed with it. `run_evaluation` works its evaluations through the dispatcher in a fresh `contextvars.Context`, and the worker asks the backend whether a claim may start before it starts one. The app creates the round and a handler's review (`starts.py`) and asks the agent to work it by id with `work_round` or `carry_round_on`. The improver's traces are one Langfuse session named after the round, and its evaluations' claims are tagged with the round as well as their run.
- `context/`: the context layer, the business's data from other systems as MCP tools. The seven files are data governance's (`data_dictionary.yaml`, `glossary.yaml`, `plans.yaml`, `claim_rules.yaml`, `reference_data.yaml`, `policy_wording.md` and `claims_manual.md`), each naming its source system, owner and review date, and the code never changes them. `files.py` reads each once when the process starts; `documents.py` splits the two documents at their numbered headings (`## <number>. <title>`) into sections tagged with document, number and title, and searches them; `lookups.py` holds the five tools over the YAML files; `answers.py` gives every answer the files it came from with their sources; `server.py` registers the seven read-only tools (`lookup_term`, `describe_fields`, `get_plan`, `get_claim_rules`, `search_reference_data`, `search_documents` and `read_section`, each with a one-line description and no optional input) on a stateless, JSON-response FastMCP server, and holds `handler`, which builds a fresh server for each request under Mangum with `lifespan="auto"` (FastMCP's session manager can run only once) and with DNS rebinding protection off, since it refuses a Function URL's host and IAM auth guards it there. `uv run -m context` serves it at `http://127.0.0.1:8006/mcp`, which `npm run dev` starts too. It has its own dependency group, `context`, and `npm run check:context` imports the server with only that group. The tests include a real server on a local port and the handler called with Function URL events.
- `dashboard/`: React, Vite and TypeScript. Handlers sign in (`auth.ts`, the one module that imports `@supabase/supabase-js`; `api.ts` sends the access token with each request and signs out on a 401), and the header shows who is signed in. Pages: the queue, a claim (the agent's steps by kind in `StepList`, a refusal standing out in the brand's alert color; `ContextUsed`, what the agent looked up in the context layer once each, grouped by file with each file's source; and `DecisionPanel`, the whole decision record with its calculation line by line; `api.ts` reads each step by its kind and refuses one it doesn't know), the Scoreboard and an evaluation (with the judge's grade and two checks for each claim), the Improvement page (start or stop a round, where it has got to, the proposal waiting with its diff and approve or reject, the rounds, a chart of each version's held-out accuracy and grade in SVG, the recipe's versions), the Configuration page (every version with its held-out scores and diff) and the Settings page. They share a page header, a navigation that marks where you are, a status pill, a table that right-aligns numbers, a diff view, empty states and a confirmation dialog built on `<dialog>`. Dark mode is an attribute on the page with the computer's choice as the default, kept by each browser. Vite reads the root `.env` for `npm run dev` only.
- `e2e/`: Playwright tests. They run the backend on SQLite and point it at stand-ins for the agent's AgentCore app (port 8003), Supabase Auth (8004, which signs tokens with a key of its own and serves its public keys) and the judge (8005), on their own ports so `npm run dev` can stay up.
- `data/`: the business data the database is first filled from. The agent never sees `data/evals/`, which holds the answer key; only seeding reads it, into tables no claim operation reads.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. The OpenRouter key is `OPENROUTER_API_KEY` in `.env`, with `DATABASE_URL` (the Supabase session pooler) and the Langfuse keys.

## Deployment

The backend and the dashboard run as one app on AWS Lambda, and nothing on Lambda seeds or creates a table: the database is made and seeded from a laptop with `npm run seed`.

- **Build:** `npm run build` (`vite build dashboard`) writes the dashboard to `dashboard/dist`. It reads `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the root `.env`, or from the environment when there is no `.env`, and bakes them into the files.
- **Server check:** `npm run check:server` imports `backend.main` in a throwaway environment holding only the `server` dependency group, so a backend import the group lacks fails there and not in the cloud. `npm run check` runs it. Keep the group in step with what `backend/` imports.
- **Package:** `uv export --only-group server`, installed for Linux and Python 3.12 (`uv pip install --python-platform x86_64-manylinux2014 --python-version 3.12 --only-binary :all:`), then `backend/`, `data/` (without `data/evals/`, the answer key, which nothing on Lambda reads) and `dashboard/dist/`, with no tests and no `__pycache__`. It zips to about 24 MB; Lambda takes up to 50 MB.
- **Handler:** `backend.main.handler`, which is Mangum around the app with `lifespan="off"`. For a web server, `backend.main:app`.
- **The dashboard** is served by the backend (`dashboard_files.py`): files at their own paths, `index.html` for any other page, and a JSON 404 for an unknown path under `/api/`. With no `dashboard/dist` the backend serves none, and `npm run dev` is unchanged.
- **Database:** with `AWS_LAMBDA_FUNCTION_NAME` set (Lambda sets it), the engine keeps one connection for the instance's next request, checked as it is taken (`pool_size=1`, `pool_pre_ping`), with no prepared statements (`prepare_threshold=None`), for Supabase's transaction pooler on port 6543, since a new connection for each request cost several trips to a database in another region. On Postgres, on Lambda or not, each statement names the schema (`schema_translate_map`) instead of relying on the connection's `search_path`, which the pooler sometimes drops.
- **Environment variables:** `DATABASE_URL`, `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`.
- **The app reads `context/` only while seeding:** never when it is imported or for a request, so its package needs no `context/`. The claims manual's version for a decision comes from the `documents` table. `pyyaml` is in the `server` group because `seed_data.py` is imported with the app.
- **The context layer's package:** `context/` without its tests, with the `context` group's packages installed for Linux and Python 3.12 (`uv export --group context`, as for the app). Its Lambda handler is `context.server.handler`, behind a Function URL with `AWS_IAM` auth, so only callers allowed to invoke it can reach it, the Gateway among them. It reads files only from its own package, writes none, and needs no environment variables. `npm run check:context` imports it with only that group.
- **The agent runs on the laptop or on AgentCore Runtime.** The app creates the agent's work itself (`backend/starts.py`: it stops work gone quiet, creates a dispatch's or an evaluation's run, a round or a review in a short transaction it commits, and asks the agent for it by id, undoing what it created when the agent didn't take it) and asks it through `backend/agent_service.py`: a payload to `/invocations` at `UNDERCOVER_AGENT` (default `http://127.0.0.1:8080`, 10 seconds, with the key as a bearer token), or, when `UNDERCOVER_AGENT_RUNTIME` is the runtime's ARN, through boto3's `invoke_agent_runtime` in a new session each time (`agent_runtime.py`: one attempt, 5 seconds to connect and 20 to read). A refusal comes through as a 409 and the work is undone; a request never sent, never connected or answered with an error starts nothing (503); a timeout or a cut-off answer may have, so nothing changes and the handler is told to reload (504). One piece of work goes at a time: a dispatch, an evaluation or a round while it works (the database's unique index on running runs with no parent decides), and a start while one is going is a 409 naming it. The agent tells the app every minute it is working a run, a round's stretch or a resumed claim, and work not heard from for five minutes (from the later of its start and the last word) is marked stopped, with the reason "The agent stopped answering", by the next start; a round's evaluation is stopped only with its round. `runtime/main.py` runs the agent's app as the platform team's `agentcore/` deploys it, with the `runtime` dependency group, which `npm run check:runtime` imports in a throwaway environment. On Runtime the three credentials come from AgentCore Identity. Its settings: `UNDERCOVER_GATEWAY_URL` (the Gateway; when set the model's tools and the payment go through it), `UNDERCOVER_CONTEXT` (the context layer, for the direct route), `UNDERCOVER_MEMORY_ID` (the memory; when set the agent keeps one), `UNDERCOVER_API` (the app, such as the one on Lambda), and the AWS credentials and region from the AWS CLI's configuration whenever `UNDERCOVER_GATEWAY_URL` or `UNDERCOVER_MEMORY_ID` is set.
