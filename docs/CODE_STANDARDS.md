# Code standards

1. Keep it simple, do not overcomplicate.
2. Comments only when necessary.
3. Be concise: a short README and no emojis.
4. IMPORTANT: avoid overly defensive code. Handle exceptions only when necessary.
5. Use uv: ALWAYS `uv run`, NEVER `python3`.
6. TypeScript: strict mode, never `any`.

7. Money: never use floats for amounts. Use `Decimal` in Python and whole cents in TypeScript, and round to the cent only when a payout is worked out. On the wire an amount is a string of dollars to the cent, such as `"420.00"`; SQLite keeps whole cents. The dashboard converts at `api.ts` and nowhere else. The judge's cost and a round's costs are whole billionths in the database, like the claim agent's, and are summed from the records. The one exception is the wire to the Gateway, whose schema says an amount is a number: `agent/gateway.py` calls `float` on a `Decimal` there and nowhere else, and a structure test allows it only there.

## Structure

Code that passes the linters can still be unfit for a pull request. These rules are about how the code is organized; reviewers check them, and `agent/tests/test_structure.py` and the ESLint config enforce what a machine can.

8. One module, one job, named for the job. Never `main.py` as a place to put things. A module never imports from another module's entry point, and two modules never share a helper by importing it from a third that is not about that helper.
9. Every outside call has one home. The claim agent reaches the backend only through `agent/api.py` and the improver only through `agent/improver_api.py`, both on the plumbing in `agent/backend_http.py`: the base URL and every path appear in those three and nowhere else, errors are handled one way, and no other agent module imports `httpx`. The claim agent's client has no way to the scores, the handlers' reasons or the rounds. The model's tools reach the app and the context layer through a route, one module for each: `agent/gateway.py` (the Gateway's tools) and `agent/direct.py` (the app with the key), with `agent/mcp_connection.py` the one place that calls MCP and `agent/sigv4.py` the one that signs; a tool never names an address or a Gateway tool. The dashboard reaches the backend only through `dashboard/src/api.ts`, which checks every response, and Supabase only through `dashboard/src/auth.ts`. The backend reaches the database only through its logic modules (`claims.py`, `runs.py`, `rounds.py`), never from a route, and the judge only through `backend/judge.py`. The backend reaches the agent only through `backend/agent_service.py`, on the plumbing of `agent_laptop.py` or `agent_runtime.py`, and the agent's work is created by the app (`backend/starts.py`), never by the agent: the agent takes it by id, on the agent's side `credentials.py` is the one module that imports AgentCore Identity and `endpoints.py` the one that reads the app's address.
   9a. The Copilot is a part of its own with the same rules. It reaches the app only through `agent/copilot_api.py`, as the signed-in handler, on `backend_http.request`; it never imports the agent's key, `send` or `api.py` (a structure test checks), and its route to the context layer refuses the app's target. Its tools are in `agent/copilot_tools.py`, at module level. The handler's sign-in is only in the turn's context and the headers of its calls, never in the state, a step, the memory or a log.
   9b. An appeal's two texts, the customer's grounds and the ombudsman's reason, come from outside the company and are read only by `backend/appeals.py`, `appeal_view.py` and `appeal_check.py` (a structure test checks), and a model reads an appeal only through `appeal_view.for_model`, which leaves out a marked appeal's texts. The check of an appeal's text has one home, `backend/appeal_check.py`, since the claims' check in `agent/screening.py` needs LangChain, which the app's package lacks. The dashboard's appeals calls are in `appealsApi.ts` on `api.ts`'s `getJson` and `post`, and only `api.ts` calls `fetch`.
10. The agent harness is separate from the business. `agent/harness.py` knows models and their settings, not claims. `agent/tools.py` holds every tool, defined at module level. A tool gets its state from `ToolRuntime[Context]` (LangChain's `context_schema`), never from a closure, a module global or a factory that builds tools per call. Entry points that wire these together are short: `agent/agents.py` wires the claim agent, `agent/improver.py` the improver (with its four tools in `agent/improver_tools.py`), and `agent/dispatcher.py`, a LangGraph graph with no model, is the only module that fans out with `Send`, and reaches the claim agent only through one function (`decide_claim`).
11. Instructions state the goal, the resources the agent has, and the rules it must not break. They are not numbered steps: a fixed sequence of steps is code, so write it as code. Point to the policy wording and the claims manual instead of copying their rules into a prompt. The improver's instructions wrap a recipe, which is data it follows and may be a list of steps; the instructions around it are goals.
12. Routes are thin. A route validates its input and calls one function in a logic module. Business rules and SQL do not live in routes. Logic modules raise `NotFound` and `Conflict`; one place in `backend/main.py` turns those into 404 and 409. Database access goes through `db.connection()`, which commits, rolls back and closes. A request holds one connection at a time: never call another logic function from inside a `with db.connection()` block, since the pool is a few connections shared by every request and two requests that each hold one and ask for another wait for each other forever, which stops the whole backend (`backend/tests/test_connections.py` checks the main flows).
13. No defensive code for states that cannot happen, and no `except` that hides a failure. The deliberate exceptions are the dispatcher worker's `error_handler`, which leaves a claim in progress for the next dispatch so that no single claim stops a run and says why in the claim's note, and a failed save to a customer's memory (`agent/memory.py`), which logs a warning and lets the claim keep its decision, since the memory only adds to what the records hold; it catches AWS's own errors and no others. A timeout is set on the client that can hang (the model, `httpx`), not simulated around it with threads.
14. Say it once. A value, a format or a block of plumbing that appears twice becomes one function (`formatMoney`, `usePolling`, `backend_http.call`). A magic string or number is a named constant in one place.
15. Tests go through public seams: the API, an agent run with a scripted model, a function's arguments. A test that patches another module's private helper is testing the shape of the code, and it will lock a bad shape in.

## Review before you hand work over

Reading your own diff as a pull request reviewer is part of the work, not a courtesy. Before every commit, go through the diff and answer these questions; if any answer is no, fix it first.

- Could I explain each module's job in one sentence, from its name?
- Does anything import something it should not need to know about (an entry point, a private name, a sibling's internals)?
- Is any URL, path, model name or other literal written in more than one place?
- Is any logic or SQL in a route, or any HTTP in a tool?
- Does any prompt read as a recipe of numbered steps?
- Is there a block of code that appears twice?
- Would a stranger reading this for the first time say "ship it"?
